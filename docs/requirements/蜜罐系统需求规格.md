# Honeypot 蜜罐系统需求规格

## 1. 产品定位

Honeypot 是一套可扩展的多协议蜜罐与威胁观测平台。系统在受控主机上监听一个或多个端口，对外表现出接近真实服务的协议特征，吸引扫描、连接、认证和协议探测行为；系统在 TCP 连接建立的第一时间记录连接证据，并把来源 IP 聚合为威胁清单，供后续查询、规则分析、告警和人工处置使用。

系统的核心价值是观测和取证。协议适配器可以模拟服务的网络行为，但不连接真实数据库、真实桌面或生产系统，不执行攻击者提交的命令，也不把蜜罐变成横向移动入口。

## 2. 目标与非目标

### 2.1 目标

- 支持 RDP、SSH、MSSQL、MySQL、MongoDB 等 TCP 服务，并允许持续扩充。
- 同一个服务实例支持多个监听端口，例如 SSH 监听 22 和 2222，RDP 监听 3389 和 33890。
- 按服务配置协议版本、服务标识、握手行为、认证响应、错误响应、延迟和连接限制，使外部客户端能够完成相应阶段的协议交互。
- TCP accept 后立即记录来源、目标、端口、监听实例和连接状态，不依赖客户端是否继续发送数据。
- 以 IP 为核心聚合连接、认证、协议异常、规则命中和会话关闭信息，实时更新威胁清单。
- 通过统一接口、配置校验、运行指标和测试样本支持新增协议适配器。
- 管理台可以配置服务实例和端口，查看实时连接、威胁 IP、事件时间线和适配器健康状态。

### 2.2 非目标

- 不承诺让 RDP、MSSQL 或其他服务达到真实生产服务的全部功能。
- 不代理真实内网服务，不把客户端请求转发到真实数据库、桌面或上游地址。
- 不执行攻击者的 SQL、Shell、PowerShell、宏、文件上传或远程桌面操作。
- 必须保存攻击者提交的原始认证要素；存储层使用加密证据仓库，普通日志、列表和接口不直接暴露原始值。
- 不在一期实现自动修改宿主防火墙；`Block` 先表示风险策略结果，真正阻断需要单独的受控执行模块和审计。

## 3. 核心概念

| 概念 | 说明 |
| --- | --- |
| ServiceAdapter | 某一种协议的代码实现，例如 SSH、MySQL、MongoDB。负责协议拟真，不负责开端口和写数据库。 |
| ServiceProfile | 拟真人格配置，例如 OpenSSH 版本、MySQL server version、RDP 的 NLA 策略。 |
| ServiceInstance | 一个可运行的逻辑服务，绑定一个适配器、一个人格和一个或多个端口。 |
| ListenerBinding | 服务实例的单个监听入口，包含 bind address、port、transport 和端口级覆盖配置。 |
| Session | 一条已接受的连接及其协议状态、超时和字节统计。 |
| InteractionEvent | 连接、握手、认证、协议异常、规则命中和关闭等不可变事件。 |
| ThreatIpProfile | 以规范化来源 IP 聚合形成的威胁档案。 |
| FidelityLevel | 协议拟真等级，表示客户端能完成到哪一个交互阶段。 |

## 4. 用户角色

- **系统管理员**：创建服务实例、配置端口、启动/停止监听、配置留存和查看审计。
- **安全分析员**：查询威胁 IP、查看事件时间线、分析协议指纹、导出证据和标记处置状态。
- **运维人员**：查看监听器健康、连接数、队列积压、存储故障和资源上限。
- **开发人员**：实现协议适配器、维护协议样本、补充回放测试和兼容性矩阵。

## 5. 功能需求

### FR-001 服务类型目录

系统维护服务类型目录，每个服务类型至少包含：协议键、显示名称、传输层、适配器版本、支持的拟真等级、支持的配置项、资源上限、兼容性说明和安全边界。

服务类型目录初期包含：`ssh`、`mysql`、`mongodb`、`mssql`、`rdp`。后续可以增加 FTP、Telnet、Redis、HTTP、SMB、VNC、LDAP、DNS、SNMP 等协议。

### FR-002 服务人格与拟真配置

管理员可以为服务实例选择或创建 ServiceProfile，配置以下内容：

- 对外服务版本、产品名称和 banner；
- 握手能力位、协议版本、加密/TLS/NLA 模式；
- 认证方式和受控失败响应；
- 错误码、断开原因、响应顺序和延迟范围；
- 空闲超时、握手超时、最大帧大小、单连接总字节数；
- 是否采集协议摘要、首包、客户端指纹和认证证据；认证证据按类型标注为 `Plaintext`、`Response`、`Ciphertext` 或 `Decrypted`。

人格配置只能使用适配器声明的能力，配置校验失败时不得启动监听。

### FR-003 多端口监听

一个 ServiceInstance 可以绑定多个 ListenerBinding。例如：

```json
{
  "instanceId": "ssh-default",
  "adapter": "ssh",
  "profile": "openssh-compatible",
  "bindings": [
    { "bindAddress": "0.0.0.0", "port": 22, "transport": "tcp" },
    { "bindAddress": "0.0.0.0", "port": 2222, "transport": "tcp" }
  ]
}
```

每个端口都必须单独显示运行状态、连接数、错误数和最近事件。事件必须保存实例、监听器和目标端口，不能只保存协议名称。

同一 `bindAddress + port + transport` 只能由一个生效监听器占用。配置保存、启动和热重载时都要检查端口冲突、端口范围、低端口权限、IPv4/IPv6 兼容性和资源上限。

### FR-004 监听生命周期

管理员可以执行创建、校验、启动、停止、禁用、重载和回滚。应用配置使用两阶段流程：

1. 校验所有适配器、人格、端口、TLS 引用和资源上限；
2. 先绑定新配置，全部成功后再切换生效状态；失败时保留旧配置，已有会话继续按原快照运行。

适配器异常只能终止当前会话，不得导致管理 API 和其他监听器一起退出。监听器必须有 `Starting`、`Running`、`Degraded`、`Stopping`、`Stopped`、`Failed` 状态。

### FR-005 协议拟真

系统按拟真等级管理能力，不用“端口开放”代替“协议可用”：

| 等级 | 能力 | 说明 |
| --- | --- | --- |
| L0 | TCP 接受 | 端口可以建立连接并按策略关闭。 |
| L1 | banner/初始响应 | 客户端能识别服务类型和基础版本信息。 |
| L2 | 协议握手 | 常见客户端能够完成初始协商，系统能解析客户端能力。 |
| L3 | 认证与有限会话 | 能解析认证尝试，返回受控成功/失败和有限会话状态。 |
| L4 | 交互式诱捕 | 对少量高价值命令提供状态化响应，不执行真实命令。 |

每个适配器必须声明已验证的等级、客户端、协议版本和已知限制。

### FR-006 连接即时记录

当监听器完成 TCP accept 时，必须立即生成 `ConnectionAccepted` 事件，至少记录：

- connectionId、eventId、sequence；
- 来源 IP/端口和目标 IP/端口；
- transport、listenerId、serviceInstanceId、adapterKey、profileId；
- UTC 时间、连接状态和数据采集策略；
- TLS/SNI（已发生时）、网络地址族和基础客户端指纹；
- 事件写入状态和降级原因。

客户端不发送任何字节后立即断开，也必须能够在事件查询中看到这条连接。

### FR-007 威胁清单

系统按规范化来源 IP 聚合威胁档案。每个档案至少包含：

- `threatId`、`sourceIp`、firstSeen、lastSeen；
- 总连接数、活动会话数、认证尝试数、协议异常数；
- 访问过的服务、实例和端口；
- 当前风险分、最高风险分、评分版本和最近命中原因；
- 状态：`New`、`Observed`、`Suspicious`、`Blocked`、`Allowlisted`、`Muted`、`Expired`；
- 最近事件、证据引用、标签、人工备注和状态变更审计。

连接事件先进入不可变事件流，再更新威胁聚合。重复事件必须幂等；风险分使用可配置因子和时间衰减，单次连接默认不会永久封禁 IP。

### FR-008 会话与事件查询

管理台和 API 支持按来源 IP、目标端口、服务类型、实例、事件类型、时间范围、风险状态和监听状态过滤。事件详情应展示同一 connectionId 下的有序时间线，包括连接、banner、握手、认证、协议异常、规则命中和关闭。

### FR-009 规则与风险策略

规则可以根据来源、端口组合、协议异常、认证失败次数、客户端指纹、时间窗口和协议字段命中。规则采用草稿、观察、生效、回滚流程，命中必须记录规则版本和风险增量。

默认策略为观察。阻断策略需要明确作用域、到期时间、审批人和回滚方式，不能由适配器直接修改宿主防火墙。

### FR-010 运行指标与告警

系统至少暴露：监听器状态、活动连接数、accept 速率、握手成功/失败、适配器异常、事件队列长度、写入延迟、丢弃数量、降级次数、威胁更新延迟和最后成功写入时间。

## 6. 协议拟真目标

| 协议 | 一期目标 | 验收重点 |
| --- | --- | --- |
| SSH | L1/L2，后续 L3 | `ssh -vv` 能看到版本交换和 KEXINIT；能解析用户名和认证方式；返回受控认证失败，不提供真实 Shell。 |
| MySQL | L1/L2，后续 L3 | `nc`/telnet 建连后收到 MySQL Initial Handshake；`mysql` 客户端能到达认证阶段；返回受控错误，不连接真实数据库。 |
| MongoDB | L1/L2，后续 L3 | 处理 wire protocol 的 hello/isMaster；返回可配置 buildInfo/能力字段；认证失败可解释，不返回真实集合数据。 |
| MSSQL | L1/L2 实验，后续 L3 | 完成 TDS PreLogin/有限 Login 响应；`sqlcmd` 可以到达受控登录失败；不执行 SQL。 |
| RDP | L2 已完成，MCS/桌面为后续 | 完成 TPKT/X.224、TLS/NLA、CredSSP/SPNEGO/NTLM Type1/Type3 认证阶段；兼容客户端能进入账号认证并收到 `STATUS_LOGON_FAILURE`，一期不实现 MCS、虚拟桌面或真实密码校验。 |

“telnet 能连上”只能证明 TCP/L1，不能证明 MySQL、MSSQL、MongoDB 或 RDP 的协议拟真已经完成。MySQL 初始包通常是二进制数据，验收应使用 MySQL 客户端、`nc` 或抓包检查协议字段。

## 7. 非功能需求

- **扩展性**：新增协议应只需实现适配器、能力描述、样本和测试，不修改监听器、事件记录和威胁聚合核心。
- **实时性目标**：在定义的基准负载下，`ConnectionAccepted` 进入可靠队列 P95 ≤ 500 ms，威胁清单可查询更新时间 P95 ≤ 1 s；实际数值必须通过压测验证。
- **可靠性**：配置应用原子切换；单个会话或适配器故障不得拖垮其他服务；服务重启不能重复占用同一端口。
- **隔离性**：数据面与管理面分离，适配器默认禁止主动访问外部网络，不允许连接真实内网服务。
- **资源边界**：每实例限制最大连接数、每 IP 速率、握手时间、空闲时间、报文大小、单会话字节数和全局队列长度。
- **可审计性**：配置、启停、重载、规则、威胁状态、证据查询和导出都记录管理员审计。
- **数据保护**：时间统一 UTC；ID 由集中 ID 组件生成；对外长整数使用字符串；原始密码和认证材料必须加密落盘，私钥仍禁止进入普通业务数据。

## 8. 关键验收场景

1. SSH 实例同时监听 22 和 2222，两端口都能完成版本交换，事件中端口和实例准确。
2. 任意客户端 TCP connect 后不发送数据立即关闭，仍能查询到 `ConnectionAccepted`。
3. MySQL 端口收到合法初始握手，`mysql` 客户端能到达认证失败阶段。
4. MongoDB 客户端能完成 hello/isMaster，系统返回受控能力信息。
5. RDP 使用 `mstsc` 发起连接，至少到达 X.224/TLS/NLA 设计目标对应阶段并有受控结果。
6. MSSQL 客户端能完成已实现的 TDS 初始协商并收到受控登录错误。
7. 同一 IP 访问多个服务和端口时聚合为一条威胁档案，并保留服务/端口明细。
8. 端口冲突、端口权限不足、握手超时、超大报文、连接超限和适配器异常都有明确结果。
9. 事件重复提交不重复增加连接计数；服务重启后不产生重复监听。
10. 关闭事件存储或制造队列积压时，系统显示降级状态、丢弃/补偿指标和可执行的恢复步骤。

## 9. 待确认的产品决策

以下事项建议在进入真实传感器和数据库实现前确认：

- 首期部署是单机传感器，还是直接考虑多节点管理；建议先做单机，再预留 Agent 注册合同。
- 服务实例与监听配置一期采用 EF Core SQLite/WAL，并通过启动迁移更新表结构；事件、威胁和证据仓库仍保留独立接口，后续再接入生产级持久化。
- 数据保留周期和原始报文上限；建议默认保留 30 天，原始数据按字段白名单和大小上限采集。
- 已确认必须保存攻击者提交的密码和认证材料。原始值进入加密证据仓库，查看、解密、导出和删除都要权限与审计；普通查询只显示掩码。
- `Block` 是否只更新威胁状态，还是联动防火墙；建议一期只标记和审计，不自动阻断。
- 管理面认证、RBAC、告警通道和对外导出权限；建议在开放真实监听前完成最小管理员认证。
- ID 服务和监听权限的运行方式；建议注入 `IIdGenerator`，低端口通过受控能力或反向端口映射解决。

## 10. 统一认证失败策略

蜜罐默认采用 `AlwaysFail` 认证策略：任何来源 IP 只要发起登录、认证或凭据协商，不论提交的用户名、密码、域、数据库名、认证方法或凭据内容是什么，都返回协议规定的失败结果，不允许登录成功，不创建真实业务会话。

系统必须保存以下攻击证据，并将其与认证事件、connectionId 和威胁档案关联：

- 来源 IP、目标端口、服务实例和 connectionId；
- 用户名、域名、数据库名或客户端标识（按字段白名单）；
- 认证方式、认证阶段、失败原因、失败码和尝试次数；
- 客户端指纹、协议版本、时间和关联威胁档案。

### 认证证据保存要求

- SSH、Telnet、FTP 等直接提交密码的协议，保存收到的原始密码值。
- MySQL、MongoDB 等 challenge-response 或加密认证，保存原始认证报文、挑战/盐、响应值，以及适配器能取得的解密后字段，并标注材料类型。
- RDP 的 TLS/NLA/CredSSP 如果已由适配器终止并解析出域、用户名和密码，保存解密后的认证字段；未能解密时保存收到的加密认证材料和握手摘要。
- MSSQL 保存 TDS 登录包、认证字段、加密状态和适配器可取得的原始凭据要素，不执行 SQL。
- 原始密码和认证材料必须进入加密证据仓库，不能写入普通应用日志、指标、异常堆栈或前端列表。
- 普通查询默认掩码；只有 `CredentialEvidence.Read` 权限可以查看原始值，查看、解密、导出和删除都写入可靠审计。
- 证据必须有 retention、加密密钥引用、材料类型、截断标记和来源事件；密钥轮换或不可用时不得假报读取成功。

协议返回要求：

- SSH 返回受控的 authentication failure，不提供 Shell 或端口转发；
- MySQL 返回协议合法的 access denied/authentication error，不建立数据库会话；
- MongoDB 返回协议合法的 unauthorized/authentication failure，不返回集合数据；
- MSSQL 返回 TDS 登录失败或受控错误，不执行 SQL；
- RDP 在达到 TLS/NLA/CredSSP/NTLM Type3 后返回协议合法的受控认证失败，不建立 MCS 或真实桌面；NTLM challenge-response 按 `Response` 证据保存，不能伪称为明文密码。

每次认证尝试都产生 `AuthenticationAttempted` 事件并增加风险分；重复失败在时间窗口内按规则累计。未来如需模拟“登录成功后的诱捕会话”，必须新增独立的显式策略、虚拟账号、权限边界和审计，不能修改 `AlwaysFail` 默认值。

## 11. 用户体系与首次初始化

系统不预置管理员账号。首次启动时用户文件为空，所有管理 API 要求先完成初始化；前端自动进入 `/setup` 初始化向导。

- 初始化接口只允许在没有用户时调用一次；第一个用户自动获得管理员角色。
- 用户密码使用 PBKDF2-SHA512、随机盐和高迭代次数保存，禁止保存明文密码。
- 登录成功后签发 Bearer 会话令牌；未携带有效令牌的管理 API 返回 401。
- 用户文件存放在受控数据目录，部署环境通过 `Honeypot__DataDirectory` 配置。
- 健康检查、初始化状态、初始化和登录接口保持公开；服务实例、监听器、事件、威胁和证据接口需要登录。
- 后续增加用户、禁用用户、角色和审计接口时，必须保留首个管理员初始化边界。
