# 协议认证补全实施方案

- 日期：2026-11-09
- 状态：已按下述范围完成实施。验证范围与未验证项见本文第四节。
- 目标：现有 SSH、MySQL、MongoDB、MSSQL、RDP 适配器对兼容客户端完成合法握手、接收认证材料，然后返回标准认证失败。所有认证保持 `AlwaysFail`，不建立 shell、桌面或数据库业务会话。

## 一、凭据采集边界

“记录账号密码”按客户端实际发送的内容实现，不把响应值、票据或公钥伪称为密码。

| 协议与认证方式 | 可记录内容 | 失败结果 |
| --- | --- | --- |
| SSH password / 密码式 keyboard-interactive | 用户名、原始密码 | SSH_MSG_USERAUTH_FAILURE |
| SSH publickey | 用户名、公钥、签名等实际提交材料；没有私钥及其口令 | SSH_MSG_USERAUTH_FAILURE |
| MySQL caching_sha2_password full-auth | 用户名、数据库、TLS 内密码或 RSA 解密密码 | 1045 / SQLSTATE 28000 |
| MySQL mysql_native_password | 用户名、数据库、scramble 和认证响应 | 1045 / SQLSTATE 28000 |
| MongoDB SCRAM-SHA-1 / SCRAM-SHA-256 | 用户名、authSource、机制、挑战与 client proof | code 18 AuthenticationFailed |
| MongoDB 显式 PLAIN | 客户端主动选择该机制时提交的账号密码；不能作为普通驱动的自动回退 | code 18 AuthenticationFailed |
| MSSQL SQL 登录 | 用户名、数据库、LOGIN7 可逆编码还原后的密码 | 18456 |
| MSSQL NTLM / RDP NLA NTLM | 用户名、域、工作站、挑战与 NTLM 响应 | TDS 登录失败 / STATUS_LOGON_FAILURE |

MongoDB 默认 SCRAM 和 RDP NLA 的 NTLM 不传输原始密码。本次不增加密码猜测或破解，也不把认证成功后的凭据委派流程作为获取密码的手段。Kerberos 票据如实际收到，只按材料类型加密记录并合法拒绝，不接入真实域或 KDC。

客户端必须支持所协商的算法并接受服务端证书/SSH 主机身份。证书不受信任、主机密钥冲突或客户端策略不允许该机制时，可能在提交凭据之前失败；不能承诺任意客户端在任何配置下都只显示密码错误。

## 二、已核实的实现缺口

1. SSH 已完成版本交换、KEX、NEWKEYS 和 password 基础，但宣告的 keyboard-interactive 没有挑战应答；none/公钥探测与实际密码提交共用认证次数；算法宣告与签名实现不完全一致。密码被写入普通事件 `Password` 字段，事件 API 会直接返回该字段。
2. MySQL 握手 capability 和字段布局不完整，使用固定 scramble，固定偏移读取用户名；没有完整解析 SSLRequest、插件、数据库和认证响应。现有首包失败不等于已取得密码。
3. MongoDB 对二进制报文做文本子串识别，没有按 BSON 顶层命令解析，可能误判 hello 中的认证协商字段；没有 SCRAM server-first/client-final，且没有正确区分 OP_QUERY 和 OP_MSG 的回复格式。
4. MSSQL 把 LOGIN7 的 HostName 字段偏移当成 Username；未实现 PreLogin 后的 TDS 封装 TLS，也未解码密码或重组多包。现有测试复用了错误字段偏移。
5. RDP 缺少 requestedProtocols 和 CredSSP 版本/状态校验；NTLM Type2 的域名 AVPair、flags 与字段布局不一致，真实客户端可能在发送 Type3 前退出。现有测试直接构造 Type3，未覆盖完整往返。
6. 多个适配器的证据 EventId 与随后认证事件的 EventId 不一致；公共存证方法在不可存储时返回虚假的 `pending-*` 引用。认证方式、失败码、尝试次数及材料类型没有统一结构化表达。
7. 证据存储是进程内 AES-GCM 密文，重启后丢失；当前证据读取只额外检查客户端请求头，缺少独立角色权限判断和读取审计，留存时间也未实际限制读取。

## 三、拟实施内容

### 1. 公共认证与证据链路

- 复用现有会话、事件接收器、证据存储和用户角色，集中实现认证记录，固定同一次认证事件与证据的关联 ID。
- 记录来源、服务实例、端口、用户名、域/数据库、认证方式、失败码、尝试次数、材料类型和 credentialArtifactId；新增模型放 Models，公共处理放 Common，接口与实现遵循现有目录约定。
- 原始密码及认证材料仅写加密证据。普通事件、API、SignalR 和管理列表不暴露原文；调整现有事件页的密码展示，显示材料类型与证据状态。
- 使用现有管理员角色限制证据原文读取，记录读取审计，并拒绝返回已过留存期的内容；不以客户端自报请求头作为授权依据。
- 存证或事件追加失败时产生明确的失败状态并终止当前会话，不伪造存储成功引用，也不回退到普通日志存密码。
- 保留现有进程内存储边界，生产持久化、数据库迁移与受控密钥托管另行安排；本次不改数据库结构、现有密钥或 .env。

### 2. SSH

- 补齐 password 和 keyboard-interactive 密码提示/响应，再返回认证失败。
- 分开限制协商探测与实际认证提交，同时设置总请求、帧长和超时上限，避免探测提前耗尽密码尝试机会。
- 校验请求服务、认证方法和算法协商；宣告能力与实际实现一致，保持无成功认证、无 channel/shell。
- 公钥路径只记录实际传来的公钥/签名，不把私钥口令作为可采集能力。

### 3. MySQL

- 修正 HandshakeV10、HandshakeResponse41、能力位、随机 scramble、包序号和字段边界，处理分片、UTF-8 用户名、数据库及插件名称。
- 支持 mysql_native_password 响应取证，以及 caching_sha2_password full-auth 的 TLS / RSA 交换分支；按实际结果标记 Plaintext、Decrypted 或 Response。
- 完成认证材料采集后返回 1045 / 28000；不返回认证 OK，不执行 SQL。

### 4. MongoDB

- 使用有界 BSON/OP_MSG 解析，正确回复旧 OP_QUERY 握手；按顶层命令处理 hello、isMaster、buildInfo、saslSupportedMechs 和 speculativeAuthenticate。
- 实现 SCRAM-SHA-1/256 的 client-first → server-first → client-final，校验会话 ID、nonce、帧边界和状态顺序，记录 proof 后返回 code 18。
- 对客户端明确选择的 PLAIN 做有界解析与取证，不诱导默认 SCRAM 客户端切换为 PLAIN。
- 保持受限的握手/监控请求交互；业务命令合法拒绝，不实现真实数据操作。

### 5. MSSQL

- 实现 TDS 7.x 有界消息重组、EOM/包类型校验、PreLogin 选项和 TDS 封装 TLS；复用已有底层流能力。
- 严格解析 LOGIN7 长度、版本及字段范围，正确读取用户名、数据库并还原密码编码；SQL 登录与 SSPI 分支分开处理。
- NTLM 分支完成 Type1 → Type2 → Type3，复用经修正的 NTLM 消息处理，采集响应后失败，不调用真实域认证。
- 修正 18456 ERROR/DONE 包并使用人格信息；不实现 SQL 执行。TDS 8.0 Strict、Kerberos 完整认证不在本次承诺范围。

### 6. RDP

- 解析 X.224 请求能力并合法选择 NLA，处理 CredSSP 版本和状态顺序。
- 修正 NTLM Type2 的 TargetName、域名/主机名 AVPairs、flags、Version 和随机 challenge，使兼容客户端能提交 Type3。
- 加密保存关联的挑战/响应与身份信息，在 Type3 后返回 STATUS_LOGON_FAILURE；仅完成认证阶段，不实现 MCS、桌面或成功后的凭据委派。

## 四、验证与验收

验收标准是客户端收到协议级认证失败，且服务端记录与本次输入对应的账号及实际认证材料。单纯断开、TLS 错误、BSON/TDS 格式错误、超时均不能算通过。

- 协议测试：使用合法握手和认证报文，覆盖空密码、非 ASCII 账号、分片/合包、超长/截断、未知机制、超时、取消、重复提交和存证失败。
- 证据测试：关联 ID 一致；密码可采集的路径解密后与隔离测试输入一致；Response 路径保留挑战/响应上下文；普通事件/API/SignalR 不含原始凭据；访问权限、审计、留存约束生效。
- 客户端验收：OpenSSH 的 password 与 keyboard-interactive；MySQL 8 兼容客户端的 full-auth 和 native 路径；MongoDB 官方驱动的 SCRAM-SHA-1/256；Microsoft.Data.SqlClient 的 18456；MSTSC 或 FreeRDP 的完整 NLA 认证失败。
- 仅使用临时回环地址与隔离样本开展协议测试，不启动真实 SSH/数据库/桌面服务，不访问共享数据库。确认本方案后实施所需的临时回环测试，结束即释放监听；不部署服务器或开放公网端口。
- 验证环境具备 .NET 10 SDK 与 OpenSSH；未安装 mysql、mongosh、sqlcmd、xfreerdp 客户端。优先使用现有工具和局部测试依赖；不安装全局依赖。无法运行的真实客户端验收单独列为未验证，不以构造报文替代。
- 后端修改后运行 `dotnet build backend/Honeypot.slnx` 和 `dotnet test backend/Honeypot.slnx`；前端修改后运行对应 lint、测试和构建。

## 五、实施顺序与回滚

先完成公共证据链路，再并行处理独立协议，最后做端到端兼容验证与文档状态更新。保持现有适配器注册和服务实例合同的兼容性；新增元数据使用可选字段，避免数据库迁移。

本次只做本地代码及测试，不执行部署、文件删除、全局安装或现有密钥配置变更。部署属于后续动作；若未来发布，保留既有发布包以便回退，不把本地构建通过写成已部署。
