# 连接事件与威胁清单设计

## 1. 目标

连接记录必须独立于协议握手。即使客户端只完成 TCP 三次握手后立即断开，系统也要留下可查询的连接证据，并在同一来源 IP 的威胁档案中增加一次观测。

应用层只能观察到已经完成 TCP accept 的连接。SYN 扫描、半连接和被宿主防火墙丢弃的报文需要独立的抓包、eBPF 或防火墙日志传感器，不能把应用层 accept 记录描述成所有网络探测。

## 2. 事件处理顺序

```text
TCP accept
  ↓
生成 connectionId / eventId / sequence=1
  ↓
记录来源、目标、端口、监听器、实例和 UTC 时间
  ↓
写入有界可靠队列或本地 WAL
  ↓
更新 ThreatIpProfile
  ↓
交给协议适配器处理 banner / handshake / auth
  ↓
按同一 connectionId 追加事件
  ↓
SessionClosed 汇总时长、字节和关闭原因
```

`ConnectionAccepted` 写入可靠队列后才进入协议处理。建议目标是在基准负载下 P95 ≤ 500 ms；该数值需要通过压测确认，不能从代码存在推导出来。

存储不可用时遵循显式 `CaptureFailurePolicy`：

- `CloseSession`：无法可靠记账时关闭会话，适合严格取证模式；
- `ContinueDegraded`：继续提供有限拟真，同时标记降级、丢弃和补偿状态，适合实验室模式。

队列、WAL、写入失败、积压、丢弃数量和最后成功时间都必须暴露指标。

## 3. 统一事件合同

每个事件至少包含：

```json
{
  "eventId": "evt_01...",
  "connectionId": "conn_01...",
  "sequence": 1,
  "eventType": "ConnectionAccepted",
  "occurredAtUtc": "2026-11-08T09:00:00Z",
  "sourceIp": "192.0.2.10",
  "sourcePort": 53001,
  "destinationIp": "192.0.2.20",
  "destinationPort": 3389,
  "transport": "tcp",
  "listenerId": "rdp-main-3389",
  "serviceInstanceId": "rdp-main",
  "adapterKey": "rdp",
  "profileId": "windows-compatible",
  "stage": "accepted",
  "outcome": "recorded",
  "payloadSummary": null,
  "captureTruncated": false,
  "riskDelta": 1,
  "ruleVersion": null
}
```

字段规则：

- `eventId`、`connectionId`、`threatId` 由集中 ID 组件生成，接口以字符串传输。
- `sequence` 在同一 connectionId 内单调递增，用于恢复事件顺序；UTC 时间用于展示和查询。
- IP 使用规范化格式，同时保存地址族；不要从代理头部推断真实来源，除非代理链路已显式配置并审计。
- `payloadSummary` 只保存协议字段摘要或受限前缀；原始认证证据通过 `credentialArtifactId` 关联加密证据仓库，不直接嵌入普通事件。
- 原始认证证据必须有材料类型、加密密钥引用、方向上限、会话上限、截断标记、权限控制和到期删除策略。

## 4. 事件类型

| 事件 | 触发点 | 最低字段 |
| --- | --- | --- |
| `ConnectionAccepted` | TCP accept 完成 | 来源/目标、端口、监听器、实例、时间、连接 ID |
| `BannerSent` | 发送服务标识或初始包 | 协议、版本、摘要、字节数 |
| `HandshakeReceived` | 收到协议握手 | 阶段、能力、耗时、结果 |
| `AuthenticationAttempted` | 解析到认证尝试 | 用户名/域、方法、结果、失败原因、credentialArtifactId；原始材料保存于加密证据仓库 |
| `ProtocolViolation` | 格式错误、异常序列或超限 | 偏差类型、关闭策略、摘要 |
| `RuleMatched` | 规则命中 | 规则 ID/版本、命中字段、风险增量、动作 |
| `CaptureTruncated` | 达到证据或资源上限 | 方向、上限、已采集字节、原因 |
| `SessionClosed` | 会话关闭 | 原因、时长、上下行字节、最后阶段 |
| `ListenerStateChanged` | 监听状态变化 | listener、旧/新状态、错误码、配置版本 |
| `StorageDegraded` | 事件存储异常 | 队列深度、丢弃/补偿状态、恢复时间 |

## 5. 威胁 IP 聚合

### 5.1 ThreatIpProfile

```text
threatId
sourceIp
firstSeenUtc
lastSeenUtc
currentScore
maxScore
scoreVersion
status
attemptCount
sessionCount
activeSessionCount
authAttemptCount
protocolViolationCount
servicesTouched[]
portsTouched[]
lastEventId
lastReason
tags[]
expiresAtUtc
```

服务和端口明细单独聚合，避免只保留一个总计：

```text
ThreatIpService(threatId, adapterKey, connectionCount, authFailures, lastSeenUtc)
ThreatIpPort(threatId, destinationPort, connectionCount, lastSeenUtc)
```

### 5.2 风险评分

评分由版本化策略计算，示例因子如下：

- 新连接：+1；
- 同一时间窗重复连接：按次数递增但设置上限；
- 同一 IP 探测多个端口：+3；
- 认证失败：+5；
- 协议异常或畸形报文：+4；
- 规则命中：按规则风险等级增加；
- 长时间无行为、超时或评分窗口结束：按时间衰减。

评分必须记录 `scoreVersion`、命中因子、风险增量和计算时间，支持幂等重放。默认状态只做 `Observed`/`Suspicious` 标记，不自动修改宿主防火墙。

### 5.3 状态流转

```text
New → Observed → Suspicious → Blocked
  └──────────────→ Allowlisted
  └──────────────→ Muted
Suspicious/Blocked → Expired（按策略到期）
```

`Allowlisted` 和 `Muted` 只影响告警与展示，不删除历史事件。任何人工状态变更都记录操作者、原因、范围、过期时间和审计事件。

## 6. 幂等与恢复

- 事件写入以 `eventId` 做唯一约束；重复投递返回原处理结果。
- 威胁聚合以事件 ID 或聚合幂等键防止重复增加计数。
- 本地 WAL/队列恢复后按 sequence 重放，重放前检查已处理游标。
- 服务重启恢复 listener desired state，但不得重复绑定已占用端口。
- 事件存储不可用时，管理台显示 `Degraded`、队列深度、丢弃数量和最后成功写入时间。

## 7. 认证证据仓库

认证证据与普通事件分开保存，但通过 `credentialArtifactId` 关联。业务上必须保留攻击者提交的原始密码或认证材料；存储层使用密文，查看时由受控服务解密。前端列表只显示掩码，原始查看、导出、复制和删除均要求 `CredentialEvidence.Read/Export/Delete` 权限并产生可靠审计。任何异常、密钥不可用或解密失败都不能回退为打印原文。

## 8. 数据留存与权限

建议一期默认保留 30 天，具体周期由部署环境确认。普通分析员可查询事件摘要和威胁聚合；原始证据、导出和状态变更需要更高权限并记录审计。原始密码不写入普通事件表，必须通过加密证据仓库保存。

## 9. 指标

至少提供：

- accepts_total、active_sessions、sessions_closed_total；
- event_append_latency、event_queue_depth、event_drop_total；
- threat_update_latency、threat_update_failure_total；
- adapter_handshake_success/failure、protocol_violation_total；
- capture_truncated_total、storage_degraded_total；
- listener_binding_failure_total、listener_restart_total。

## 10. 认证失败事件规则

系统默认所有认证尝试均为失败。`AuthenticationAttempted` 的 `outcome` 使用 `failure`、`rejected` 或 `invalid`，不得出现成功结果；事件至少关联来源 IP、目标端口、服务实例、认证方式、失败码和威胁档案。

登录失败不等于连接立即关闭：协议适配器可以按拟真等级返回一次或多次协议合法的失败响应，然后按人格策略关闭会话。无论客户端提交何种账号或凭据，都不得创建真实业务会话；原始凭据通过 `credentialArtifactId` 保存到加密证据仓库，不直接写入事件正文。

认证证据建议包含以下字段：

```text
credentialArtifactId
connectionId
eventId
sourceIp
adapterKey
materialType       # Plaintext / Response / Ciphertext / Decrypted
contentCiphertext
encryptionKeyRef
capturedAtUtc
retentionUntilUtc
truncated
```
