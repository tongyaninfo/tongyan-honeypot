# 多协议服务适配与拟真设计

## 1. 设计原则

协议适配器只负责协议行为，监听编排器负责端口和连接生命周期，事件接收器负责可靠记录，威胁引擎负责聚合和评分，管理 API 负责配置、查询和审计。任何适配器都不能自行开端口、直接写数据库、访问宿主命令或连接真实上游。

数据流如下：

```text
ListenerHost
    ↓ accept
ConnectionAccepted（立即写入可靠队列）
    ↓
ThreatAggregator（更新 IP 威胁档案）
    ↓
ProtocolAdapterSession（banner / handshake / auth / limited interaction）
    ↓
InteractionEvent（按 sequence 追加）
    ↓
EventStore / Audit / Metrics
```

## 2. 目标分层

```text
Honeypot.Shared
  ├─ DTO、ApiResult、枚举、事件合同

Honeypot.Engine
  ├─ 风险评分、规则匹配、威胁聚合、幂等

Honeypot.Runtime
  ├─ ListenerHost、端口绑定、SessionManager、超时、限流

Honeypot.Protocol.Abstractions
  ├─ 适配器接口、会话接口、能力描述、配置校验合同

Honeypot.Protocols.Ssh / MySql / Mongo / MsSql / Rdp
  ├─ 各协议适配器、人格配置、协议回放样本

Honeypot.Persistence
  ├─ 事件存储、威胁档案、配置版本、证据索引

Honeypot.Api
  ├─ 管理 API、认证、RBAC、审计、运行状态查询
```

当前仓库已经实现 `Shared / Protocol.Abstractions / Runtime / Protocols.* / Engine / Api` 的首期闭环；服务实例和监听端口已使用 EF Core SQLite 持久化并在启动时增量迁移，管理台实时状态使用带当前会话鉴权的 SignalR。事件/证据生产级持久化和密钥托管仍属于后续实现计划，文档中的目标结构不代表全部完成。2026-11-09 确认认证蜜罐只推进至凭据采集和合法登录失败，真实 shell、数据库会话及 RDP 桌面不在实现范围。

## 3. 适配器接口

建议把稳定接口放在 `Honeypot.Protocol.Abstractions`，协议项目只引用它和 `Honeypot.Shared`：

```csharp
public interface IHoneypotServiceAdapter
{
    ServiceAdapterDescriptor Descriptor { get; }

    ValueTask<AdapterValidationResult> ValidateAsync(
        ServiceProfile profile,
        CancellationToken cancellationToken);

    ValueTask HandleAsync(
        IHoneypotSession session,
        ServiceProfile profile,
        IInteractionEventSink eventSink,
        CancellationToken cancellationToken);
}

public interface IHoneypotSession
{
    string ConnectionId { get; }
    EndPoint RemoteEndPoint { get; }
    EndPoint LocalEndPoint { get; }
    string Transport { get; }

    ValueTask<int> ReadAsync(
        Memory<byte> buffer,
        CancellationToken cancellationToken);

    ValueTask WriteAsync(
        ReadOnlyMemory<byte> buffer,
        CancellationToken cancellationToken);

    ValueTask CloseAsync(
        SessionCloseReason reason,
        CancellationToken cancellationToken);
}

public interface IInteractionEventSink
{
    ValueTask<EventAppendResult> AppendAsync(
        InteractionEvent interactionEvent,
        CancellationToken cancellationToken);
}
```

`IInteractionEventSink.AppendAsync` 返回成功，表示事件已经进入可靠队列或本地 WAL；仅进入内存集合不能算作“已记录”。适配器只接触受限的会话流和配置快照，不获得任意 socket、文件系统、进程或外部网络能力。

适配器注册使用静态 DI 和 `IProtocolAdapterRegistry`。第一期不加载任意 DLL；未来插件化时必须增加受信目录、签名、版本和能力清单校验。

## 4. 服务配置模型

### 4.1 ServiceProfile

负责协议拟真人格，不包含端口和运行状态：

- `profileId`、`name`、`adapterKey`、`adapterVersion`；
- `advertisedProduct`、`advertisedVersion`、`banner`；
- `fidelityLevel`、`tlsMode`、`nlaMode`、`authMode`；
- `responsePolicy`：错误码、断开原因、延迟和重试；
- `capturePolicy`：字段白名单、首包上限、方向上限和截断策略；
- `resourcePolicy`：最大帧、连接、空闲时间、握手时间和单会话字节数。

### 4.2 ServiceInstance

负责一个逻辑服务及其端口集合：

- `instanceId`、`displayName`、`adapterKey`、`profileId`；
- `desiredState`、`currentState`、`configVersion`；
- `bindings[]`、`lastApplyResult`、`lastError`；
- `createdAtUtc`、`updatedAtUtc`、`updatedBy`。

### 4.3 ListenerBinding

每个绑定独立统计和健康检查：

- `listenerId`、`bindAddress`、`port`、`transport`；
- `enabled`、`tlsCertificateRef`、`perPortOverrides`；
- `maxConnections`、`maxConnectionsPerIp`、`acceptRateLimit`；
- `state`、`activeConnections`、`acceptedCount`、`errorCount`。

生效唯一键为 `bindAddress + port + transport`。配置应用前必须检查端口冲突、端口范围 1–65535、IPv4/IPv6、低端口权限、TLS 引用和适配器能力。

## 5. 配置应用与会话生命周期

1. 管理 API 保存草稿配置并产生版本号。
2. `Validate` 检查端口、适配器、人格、证书引用、资源上限和冲突。
3. `Apply` 按新版本先创建 listener；所有绑定成功后更新 current state。
4. 新连接使用新配置快照，已有连接继续使用旧快照直到关闭。
5. 任一绑定失败时释放新绑定，保留旧版本并记录审计。
6. `Stop` 只拒绝新连接，已有会话按超时和关闭策略结束。

## 6. 拟真等级与协议适配边界

- **L0 TCP**：accept、限速、超时和关闭。
- **L1 Banner**：版本字符串或初始协议包。
- **L2 Handshake**：完成常见客户端初始协商并解析能力。
- **L3 Authentication**：解析用户名、域、认证方法和结果，返回受控错误。
- **L4 Limited Interaction**：只实现明确列出的安全命令/请求，其他请求统一拒绝或关闭。

协议适配器不得宣称超出已验证等级的能力：

- SSH 已完成版本交换、KEX/NEWKEYS、password 和 keyboard-interactive 认证失败；不提供 Shell。
- MySQL 已实现 HandshakeV10、TLS/RSA caching_sha2_password full-auth 和 native 响应采集，返回 1045；不执行 SQL。
- MongoDB 已实现 hello/isMaster、buildInfo、SCRAM-SHA-1/256 多轮和显式 PLAIN，返回 code 18；不返回集合数据。
- MSSQL 已实现 TDS 7.x PreLogin/TLS/LOGIN7 密码采集和 NTLM/SSPI 多轮，返回 18456；不执行 SQL，TDS 8 Strict 尚不支持。
- RDP 已实现 TPKT/X.224、TLS/NLA、CredSSP/SPNEGO/NTLM Type1/Type3 的最小认证链路；一期目标是 MSTSC/兼容客户端进入账号认证阶段后返回协议合法的 `STATUS_LOGON_FAILURE`，不验证密码、不实现 MCS 和真实桌面。

## 7. 资源与安全策略

每个 listener 和 session 都需要上限：连接数、每 IP 连接速率、握手超时、空闲超时、最大帧、单方向字节数、总会话时长和事件队列长度。超限必须产生 `ResourceLimitExceeded` 或 `ProtocolViolation` 事件。

管理面端口和诱捕端口分离。适配器默认无主动外联能力，不读取宿主文件，不启动进程，不执行命令，不连接数据库，不访问云元数据地址。TLS 私钥只引用受控密钥存储，不能写进 ServiceProfile 或数据库普通字段。

## 8. 测试与兼容性矩阵

每个适配器必须包含：

- 正常握手样本；
- 空连接、立即关闭、慢速发送、超大帧和畸形报文；
- 协议版本和能力位边界；
- 认证尝试并保存加密认证证据，材料类型和解密能力必须标注；
- 超时、取消、适配器异常和事件写入失败；
- 至少一个真实客户端或官方命令行工具的兼容性记录。

当前实际验证与未验证项见[协议认证补全实施方案](协议认证补全实施方案.md)。RDP 的构造客户端测试不能替代 MSTSC/FreeRDP 实测。

兼容性矩阵按 `adapter + profile + client + clientVersion + fidelityLevel + result` 维护。只有矩阵中标记为通过的阶段，才能写入已验证能力。

## 9. 统一认证失败策略

所有协议人格默认配置 `authMode = AlwaysFail`。适配器可以解析认证阶段并返回协议合法的失败响应，但不得验证真实密码、访问真实账号、建立真实数据库/桌面会话或执行认证后的命令。认证失败不影响取证：适配器必须把收到的原始认证要素送入证据仓库。

认证事件记录用户名、域/数据库名、认证方式、客户端指纹、失败码、次数和 `credentialArtifactId`。密码、私钥、完整票据和可复用认证材料保存为加密证据，不进入普通日志、指标或未授权 API；材料标记为 `Plaintext`、`Response`、`Ciphertext` 或 `Decrypted`。MySQL challenge-response、RDP CredSSP 等协议如果只能取得加密或响应值，不能把它们伪称为明文密码。

`AuthenticationAttempted` 写入后必须更新来源 IP 的风险分和威胁档案。即使用户名为空、密码错误、协议字段异常或客户端发送了未知认证方式，也要返回失败/拒绝结果并记录失败原因；不能通过异常路径让某个账号意外登录成功。
