# ADR-001：多协议服务适配架构

- 状态：已提出，待实现验证
- 日期：2026-11-08

## 背景

系统需要模拟 RDP、SSH、MSSQL、MySQL、MongoDB 等服务，并且服务类型会持续扩充。同一服务可以绑定多个端口，所有连接需要立即记录并更新 IP 威胁清单。如果把端口监听、协议解析、数据库写入和风险判断放在每个服务实现中，新增协议会复制大量基础代码，连接记录也容易受协议握手成功与否影响。

## 决策

采用以下分层：

1. `ListenerHost` 统一负责 TCP/UDP 监听、端口冲突、连接上限、限速、超时和会话生命周期。
2. `IHoneypotServiceAdapter` 负责某一协议的 banner、握手、认证和有限交互，不自行开端口、不直接写库、不访问真实上游。
3. `ServiceProfile` 管理服务人格和拟真行为；`ServiceInstance` 管理一个逻辑服务；`ListenerBinding` 管理单端口入口。
4. `IInteractionEventSink` 在协议处理前接收 `ConnectionAccepted`，先写可靠队列/WAL，再更新威胁聚合。
5. `ThreatEngine` 独立计算风险分、状态和规则命中，默认只观测，不直接联动宿主防火墙。
6. 第一阶段使用静态 DI 注册内置适配器，未来插件化必须有受信目录、签名、版本和能力校验。

## 替代方案

- 每个协议独立开一个服务进程：隔离性好，但配置、端口、事件和运维重复，暂不作为第一阶段主结构。
- 直接运行真实 MySQL/Mongo/RDP 再伪造数据：拟真度可能较高，但会引入真实服务漏洞、数据泄露和横向移动风险，不采用。
- 仅开放 TCP 端口并返回字符串 banner：实现简单，但无法满足客户端协议探测和握手兼容要求，不采用。
- 适配器直接写数据库：短期开发快，但会耦合协议与存储，无法保证连接即时记录的一致流程，不采用。

## 影响

- 新增协议主要增加 `Protocols.<Name>`、人格配置、协议样本和兼容性测试。
- 监听、事件、威胁聚合和管理 API 可以复用。
- RDP 和 MSSQL 的高拟真仍需较大协议实现和隔离测试，不能按普通 banner 服务估算工作量。
- 需要为运行时、事件存储和适配器会话增加可观测性与资源上限。

## 验证方式

- 同一 SSH 实例绑定两个端口，两个端口均可握手且事件端口准确。
- 客户端只建立 TCP 连接即断开时，`ConnectionAccepted` 仍可查询。
- 适配器异常只影响当前会话；事件队列故障能显示降级并按策略关闭或继续。
- 使用 SSH、MySQL、Mongo 客户端，以及 RDP/MSSQL 的阶段性客户端验证记录拟真等级。
